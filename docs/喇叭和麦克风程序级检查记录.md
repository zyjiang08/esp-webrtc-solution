## 一、为什么 `peer_demo` 不能直接检查喇叭/麦克风

`peer_demo` 当前的音频路径不是“真实麦克风采集 + 喇叭播放”，而是测试用的数据流：

- 发送侧在 `send_cb()` 中构造了一段 64 字节的假音频数据，然后直接发送：
  - `esp-webrtc-solution/solutions/peer_demo/main/webrtc.c:69`
- 接收侧的 `peer_audio_data_handler()` 只打印收到的包大小和首字节，并没有播放到喇叭：
  - `esp-webrtc-solution/solutions/peer_demo/main/webrtc.c:144`

也就是说：

- `peer_demo` 可以验证 WebRTC 音频收发逻辑是否通
- 但它**不能**直接验证：
  - 麦克风硬件是否真的在采样
  - 喇叭是否真的在出声

因此，如果目标是检查板子的音频硬件状态，必须换成带本地音频回环的程序。

---

## 二、用于检查音频硬件的程序路径

仓库里已经有现成的本地回环测试命令：

- `doorbell_demo` 中注册了 `rec2play` CLI：
  - `esp-webrtc-solution/solutions/doorbell_demo/main/main.c:113`
  - `esp-webrtc-solution/solutions/doorbell_demo/main/main.c:178`

该命令底层会调用：

- `test_capture_to_player()`：
  - `esp-webrtc-solution/solutions/doorbell_demo/main/media_sys.c:212`

这个函数会执行以下流程：

1. 配置音频采集参数：`G711A / 8000Hz / 单声道 / 16bit`
2. 打开 capture sink
3. 创建音频播放流
4. 启动采集
5. 循环读取采集到的音频帧
6. 将音频帧送入 `av_render_add_audio_data()` 播放

这本质上就是：

**麦克风 -> 采集链路 -> 音频渲染 -> 喇叭**

因此它是检查喇叭和麦克风是否正常的合适程序。

## 五、需要注意的点

### 1. `peer_demo` 本身不适合做音频硬件检查

如果后续还想检查喇叭/麦克风：

- 不要直接用 `peer_demo`
- 应优先用 `doorbell_demo` 的 `rec2play`

### 2. 测试前最好先停止 WebRTC 占用

`doorbell_demo` 会在联网后自动尝试入会。

如果直接执行 `rec2play`，音频链路可能与原有 WebRTC 逻辑重叠，导致：

- 播放器被占用
- 日志里出现一次性音频渲染错误

本次实际测试也验证了：

- **先 `leave` 再 `rec2play`**，结果更干净、更可靠。

### 3. 仍建议做现场听感确认

虽然程序日志已经足以说明“设备驱动和采集/播放链路是通的”，但仍有一类问题日志无法完全替代：

- 喇叭音量过低
- 麦克风增益偏小
- 有底噪/啸叫/失真
- PA 或喇叭物理连接异常但驱动未报错

因此最终建议是：

1. 运行 `rec2play`
2. 对着麦克风说话/轻敲麦克风附近
3. 现场确认喇叭是否能听到明显回声或敲击声
